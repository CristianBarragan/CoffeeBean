# M0.7 — Resolution Boundary Freeze

## Purpose

Freeze resolution around the contract defined by the ground-up architecture:

```text
SemanticRequest + Static Semantic Model
                    |
                    v
             SemanticRequestResolver
                    |
                    v
             Request SemanticGraph
```

The resolver answers whether a requested semantic structure exists. It does not
resolve database records, choose joins, generate SQL, or depend on GraphQL.

## Changes

- Removed the unused `EntityResolver` / `ICandidateSource` / candidate-evidence path
  from the core semantic resolution namespace. That path was a data/entity lookup
  mechanism rather than request-graph resolution and had no callers in the new
  architecture.
- `SemanticRequestResolver` now rejects an empty selection set.
- Repeated relationship selections must be merged by an adapter before semantic
  resolution. The resolver rejects duplicates so the canonical graph cannot contain
  accidental duplicate relationship subtrees.
- `SemanticModelBuilder` now validates duplicate entity IDs, duplicate field IDs or
  names, duplicate relationship IDs or names, identity-field declaration, and
  relationship targets.
- Added boundary tests proving resolution can operate with only the semantic model
  and request; no provider metadata is required.

## Explicit non-responsibilities

Resolution does not:

- inspect SQL tables or columns
- create joins
- access a database
- invoke a provider
- interpret GraphQL ASTs
- perform authorization
- produce an execution plan

Those concerns remain later stages in the pipeline.
