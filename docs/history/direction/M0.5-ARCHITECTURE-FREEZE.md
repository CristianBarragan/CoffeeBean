# M0.5 — Architecture Freeze / Reconciliation

## Purpose

This checkpoint reconciles the current Foundgine implementation with the ground-up architecture defined by the porting guide.

The goal is not to add another feature. The goal is to prevent the current implementation from becoming a renamed copy of the historical repositories and to freeze the provider-neutral contracts before further feature work.

## Target sequence

1. Semantic Foundation
2. Resolution
3. Authorization
4. Planning
5. SQL Execution
6. AOT
7. GraphQL Adapter

Mutations and advanced GraphQL features are downstream capabilities, not foundational architecture.

## Current assessment

## Architectural rules

The following remain non-negotiable:

- Semantic types must not depend on SQL, GraphQL, EF, Dapper, or a concrete provider.
- Planning must produce provider-independent execution concepts.
- SQL belongs below the provider boundary.
- GraphQL is an adapter and must translate into Foundgine contracts.
- AOT generates/populates metadata; it does not define the runtime architecture.
- Historical repositories are evidence for proven techniques, not a class-by-class migration checklist.

## Metadata review

The current metadata contains logical identities as well as storage mappings. This is acceptable only while the mapping remains metadata consumed by providers rather than semantic concepts.

The metadata review identified physical join objects as unnecessary at the current boundary. `JoinMetadata`, `JoinCondition`, `JoinKind`, and `StorageEntityId` were removed. `ColumnReference` and storage-name mappings remain because they are explicit domain-to-storage mapping facts consumed below the semantic layer.

See [M0.6 — Metadata Boundary Freeze](M0.6-METADATA-BOUNDARY.md).

## Mutation review

The existing mutation subsystem is intentionally retained for now because it is already part of the working repository. It must not become the template for the foundational architecture.

Before adding further mutation features, verify that the mutation pipeline follows the same separation:

`semantic mutation → provider-independent mutation plan → provider mutation plan → provider execution`

## GraphQL review

The existing GraphQL adapter is downstream of the semantic model. Keep GraphQL-specific syntax and AST handling in the adapter. Do not introduce GraphQL concepts into semantic or planning contracts merely to support advanced GraphQL syntax.

## Cleanup completed at this checkpoint

- `obj/`

## Follow-up completed

The metadata boundary review was completed in M0.6. Relationship metadata now uses explicit source/target key references rather than physical join objects. See [M0.6 — Metadata Boundary Freeze](M0.6-METADATA-BOUNDARY.md).

## Immediate next work

Do not add M31-style feature milestones yet.

The next architectural work should be a focused audit of the M1–M7 contracts, especially metadata/storage mapping and the exact provider boundary. Once those contracts are frozen, advanced mutation and GraphQL capabilities can continue without redefining the core.
