# M0.6 — Metadata Boundary Freeze

## Purpose

Freeze the metadata contract before further feature work.

The metadata layer describes the domain and its mapping to provider-consumable storage facts. It must not become a generic join/planning layer.

## Relationship mapping

`RelationshipMetadata` now contains only:

- relationship identity;
- source entity;
- target entity;
- relationship name;
- source key reference;
- target key reference.

The old physical join concepts were removed from the metadata contract:

- `JoinMetadata`
- `JoinCondition`
- `JoinKind`
- `StorageEntityId`

A provider can turn the two key references into its own join expression without requiring a join object in the semantic metadata model.

## Resulting boundary

```text
EntityMetadata
FieldMetadata
RelationshipMetadata
ColumnReference
        │
        ▼
Semantic model
        │
        ▼
Planning
        │
        ▼
Provider compiler
        │
        ▼
SQL join expression
```

The semantic layer therefore knows that a relationship connects two entities and which domain columns correlate, but it does not know whether a provider implements that correlation as an SQL `JOIN`, a correlated subquery, an API call, or another mechanism.

## Storage names

`EntityMetadata.StorageName` and `ColumnMetadata.StorageName` remain mapping data. They are consumed by providers and are not referenced by `Foundgine.Semantics` or `Foundgine.Planning`.

## AOT

The source generator emits the same metadata contract. It no longer emits a provider-specific join kind.

## Mutation impact

Nested mutation planning now consumes `RelationshipMetadata.SourceKey` and `TargetKey` directly. The mutation planner does not depend on a physical join representation.

## Acceptance

The Banking proof continues to represent:

```text
Customer
   └── Accounts
         └── Transactions
```

with explicit source/target key mappings.

The SQL provider derives its join predicates from those mappings.
