# M0.10 — Provider Boundary Freeze

## Goal

Freeze the provider boundary so provider-independent execution contracts do not
know SQL types or provider-specific mutation planning types.

## Boundary

```text
ExecutionPlan / MutationPlan
        ↓
provider compiler
        ↓
ProviderPlan / ProviderMutationPlan
        ↓
IExecutionProvider / IMutationExecutionProvider
        ↓
provider implementation
```

`ProviderPlan` and `ProviderMutationPlan` are opaque execution contracts.
Provider-specific physical details remain below the boundary.

## Mutation correction

The previous execution mutation contract exposed `MutationOperation` and
`MutationDependency` from `Foundgine.Planning.Mutation`. That made the provider
boundary aware of planning details.

M0.10 removes that coupling. `ProviderMutationPlan` is now an opaque base
record, and `ProviderMutationBatchPlan` contains only provider mutation plans.
A provider may carry dependency/order information in its own concrete batch
plan.

For SQL, `SqlMutationBatchPlan` retains the dependency information because SQL
compilation and execution own the physical realization of the mutation batch.

## SQL ownership

The SQL project may depend on:

- Abstractions
- Metadata
- Semantics
- Planning
- Execution

because SQL is the downstream provider/compiler layer.

The inverse dependency is prohibited: Execution, Planning, Semantics, and
Abstractions must not reference `Foundgine.Sql`.

## Result

The stable architecture is:

```text
Metadata
   ↓
Semantics
   ↓
Planning
   ↓
Execution contracts
   ↓
Provider compiler
   ↓
SQL / other provider
```
