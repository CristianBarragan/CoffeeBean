# M0.9 — Planning Dependency Audit

## Decision

`Foundgine.Planning` intentionally depends on `Foundgine.Semantics`.

This is not an architectural leak. Planning consumes the output of the semantic
layer and must therefore understand semantic requests, semantic graphs, filters,
and query options.

The dependency is strictly one-way:

```text
Abstractions
    ↑
Semantics
    ↑
Planning
    ↑
Execution
    ↑
Provider
```

## Why the dependency is legitimate

The planner consumes:

- `SemanticGraph` — the authorized logical request topology.
- `SemanticGraphNode` — semantic entity/relationship selections.
- `SemanticQueryOptions` — query semantics that must survive into the logical plan.
- `SemanticFilterExpression` — provider-neutral filter semantics used by mutation planning.

These are semantic concepts, not physical-provider concepts.

Removing the dependency by copying these types into Planning would create a second
semantic vocabulary and would make the architecture worse, not simpler.

## What Planning must not consume

Planning must remain independent of:

- `Foundgine.Metadata` implementation types.
- SQL/storage names.
- SQL expressions or commands.
- Hot Chocolate types.
- SQLite/provider types.
- Provider execution strategies.

`ExecutionPlan` exposes only stable identities, logical operations, semantic query
options, and child topology.

Mutation planning uses the narrow `IMutationSchema` contract from
`Foundgine.Abstractions`, rather than depending directly on `Foundgine.Metadata`.

## M0.9 conclusion

No new abstraction is warranted here. `Planning → Semantics` is a required
architectural dependency and should remain frozen.

The next boundary to scrutinize is execution/result materialization rather than
further decomposing Planning.
