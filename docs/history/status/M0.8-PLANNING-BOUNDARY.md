# M0.8 — Planning Boundary Freeze

## Purpose

Freeze the provider-independent planning boundary before further feature work.

## Rules

1. `Foundgine.Planning` consumes an authorized `SemanticGraph`.
2. `ExecutionPlan` contains only logical execution concepts and stable identities.
3. Query planning must not contain SQL, provider types, storage names, joins, aliases, or database APIs.
4. Stable identity types (`EntityId`, `FieldId`, `RelationshipId`, `ColumnId`) belong to `Foundgine.Abstractions`, not the metadata implementation layer.
5. Providers decide how `Scan` and `Traverse` are physically executed.
6. Mutation planning remains a post-M7 subsystem and is not allowed to redefine the query planning contract.

## Boundary proof

`ExecutionPlan` and `ExecutionPlanNode` may reference stable identity contracts, but they must not expose metadata objects such as `EntityMetadata`, `RelationshipMetadata`, `ColumnReference`, or provider-specific objects.

The planner also does not resolve storage, choose SQL syntax, or perform database access.

## Mutation note

The existing mutation planner remains intentionally outside the foundational M1–M7 query contract. It can use metadata to validate mutation relationships, but its abstractions must not be introduced into the query planner merely for reuse.
