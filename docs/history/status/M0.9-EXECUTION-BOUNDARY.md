# M0.9 — Execution Boundary Freeze

## Goal

Freeze the execution layer as the consumer of provider-independent plans and
semantic models, without pulling metadata or provider-specific concepts back
into `Foundgine.Execution`.

## Boundary

```text
Authorized SemanticGraph
        |
        v
   Foundgine.Planning
        |
        v
     ExecutionPlan
        |
        v
   Foundgine.Execution
        |
        +---- ResultMaterializer ----> SemanticModel
        |
        v
    ProviderPlan
        |
        v
      Provider
```

`Foundgine.Execution` owns execution contracts and result reconstruction. A
provider owns physical plan compilation and physical execution.

## Rules

- Execution does not reference `Foundgine.Metadata` directly.
- `ExecutionPlan` is the provider-independent input to execution.
- `ProviderPlan` is opaque to the core execution orchestration.
- `ExecutionResult` contains provider values plus stable `EntityId`/`FieldId`
  cell identities for result materialization.
- Result materialization uses `SemanticModel`, not storage metadata.
- Mutation result materialization validates entity/relationship topology against
  `SemanticModel` rather than `IMetadataProvider`.
- SQL-specific types remain in `Foundgine.Sql`.

## Result flow

```text
ProviderPlan
    |
    v
IExecutionProvider
    |
    v
ExecutionResult
    |
    v
ResultMaterializer + SemanticModel
    |
    v
MaterializedResult
```

For mutations:

```text
ProviderMutationBatchPlan
    |
    v
IMutationBatchExecutionProvider
    |
    v
MutationBatchResult
    |
    v
MutationResultMaterializer + SemanticModel
    |
    v
MutationMaterializedResult
```

## M0.9 conclusion

The execution boundary is frozen. Further provider-specific work should stay
below `Foundgine.Execution`, while semantic result shaping should depend on the
semantic model rather than physical metadata.
