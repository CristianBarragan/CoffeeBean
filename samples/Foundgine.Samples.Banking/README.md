# Foundgine.Samples.Banking

The canonical proof of the Foundgine thesis: can Foundgine describe a
domain, allow a dynamic planner to reason over it, and hand an execution
plan to a provider that actually runs it?

```
Domain
   ↓
Foundgine.Metadata      (hand-written — see Metadata/BankingMetadata.cs)
   ↓
Foundgine.Planning      (QueryPlanner: Intent + JoinGraph -> QueryPlan,
                          no domain-specific "if Customer then join
                          Account" logic anywhere)
   ↓
Foundgine.Builders      (logical QueryPlan)
   ↓
Foundgine.Providers     (SqlPlanCompiler -> ProviderPlan, SqlTextTranslator
                          -> SQL, SqlExecutionProvider -> real rows)
   ↓
SQLite (in-memory, shared-cache — no external server needed)
```

No GraphQL. No HotChocolate. No `Graphgine.*` project anywhere in
`Foundgine.Samples.Banking.csproj`'s dependency graph — that's the entire
point. Run it with:

```
dotnet run --project samples/Foundgine.Samples.Banking
```

It walks Customer -> Account -> Transaction end to end: the planner
discovers both joins from metadata (it is never told the domain shape
directly), the SQL provider compiles and runs the resulting query against a
real SQLite database seeded in-process, and the sample prints the joined
rows it gets back. This is the first Banking E2E from the root README's
`🔴 NOW` checklist — every step above is real, nothing is stubbed.

restructure — it's future work, not deleted — since this one is now the

folders side by side.
