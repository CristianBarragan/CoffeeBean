Benchmark methodology

Agent End-to-End Token Measurement Method

How the benchmark estimates agent-facing context load, and where that estimate is and isn't reliable.

Purpose

The Foundgine end-to-end benchmark measures how much agent-facing context is generated by a conventional application/tool choreography versus a Foundgine semantic choreography.

Current estimation method

The repository deliberately uses the same method used by the current benchmark state:

tokens ≈ max(chars / 4, words × 1.3)

For each recorded tool invocation, the benchmark estimates tokens independently for:

  • the serialized tool input payload;
  • the serialized tool output payload.

The benchmark then adds the fixed system prompt and scenario request once per run. Therefore:

estimated_context_load
  = estimate(system_prompt)
  + estimate(scenario_request)
  + Σ estimate(tool_input_i)
  + Σ estimate(tool_output_i)

This is intentionally not a full model prompt reconstruction. It is a controlled comparison of the application/tool payload burden imposed on the agent loop.

Accuracy and caveats

For payloads of the English/JSON shape used by this benchmark, this approximation is intended to track real BPE tokenizers within roughly ±15% as an order-of-magnitude heuristic. It is not a substitute for provider-reported usage.

In particular, the estimate does not include:

  • hidden model reasoning tokens;
  • model-generated response tokens;
  • tokenizer-specific special tokens;
  • exact repeated message history sent on every API call;
  • exact tool-schema tokenization.

Those omissions are intentional and must be disclosed with every published estimate.

Live mode

When a live OpenAI-compatible endpoint returns usage fields, the benchmark records:

  • input/prompt tokens;
  • output/completion tokens;
  • total tokens;
  • cached input tokens when exposed by the provider.

Those provider-reported values are the authoritative API-token measurements. The heuristic remains in the report so that its error can be compared against provider usage over time.

Why both numbers matter

Agent context load
        ≠
Provider-reported API usage
        ≠
Application execution time

A semantic execution boundary may reduce agent/tool payloads while increasing deterministic application work. The benchmark must show that trade-off rather than collapsing everything into a single "faster" or "cheaper" claim.
