Foundgine / Security
Policy-aware execution

Security is a boundary, not a magic trick.

Foundgine makes authorization and execution constraints explicit, inspectable, and enforceable. It does not make an incorrect business policy correct.

Three trust boundaries

Probabilistic

Intent interpretation

An agent or caller may misunderstand a business request. Foundgine treats incoming structured intent as untrusted input.

Deterministic

Semantic execution

The application-defined semantic model, authorization policy, plan validation, and provider contract form the controlled execution boundary.

Application / infrastructure

Operational security

Authentication, secrets, transport security, rate limiting, database permissions, deployment hardening, and identity administration remain outside Foundgine.

Authorization follows the plan

A policy is not reduced to a single Authorize() check. Conditions can be represented as semantic predicates and carried into planning. For a multi-tenant application, the security meaning can include:

resource.TenantId == user.TenantId

Planning and provider execution must preserve the required security contract. Capability discovery is advisory; execution re-evaluates the configured policy.

Semantic correctness is separate

Authorization can be perfectly enforced against the wrong business definition. For example, “affordability” may not mean balance > amount; it may depend on pending transactions, regulatory holds, available credit, or other domain rules.

Foundgine can enforce the defined meaning. The application team still owns the correctness of that meaning.

What Foundgine does not claim

Foundgine does not claim that AI interpretation is infallible, that a business policy is automatically correct, or that application/infrastructure security disappears.

The stronger claim is narrower: once application meaning and policy are defined, Foundgine provides a deterministic semantic boundary through which callers and providers must pass.
