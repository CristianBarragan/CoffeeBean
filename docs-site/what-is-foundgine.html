What is Foundgine?

Foundgine is the layer between application meaning and physical execution. It lets callers express intent without giving them direct authority over storage or implementation details.

The semantic boundary

A persistence model describes how data is stored. A semantic model describes what the application exposes and what operations mean. They can be deliberately different.

Persistence model                 Semantic model
Customer                           Customer
 ├─ Id                               ├─ id
 ├─ TenantId                         ├─ name
 ├─ Name                             └─ accounts
 ├─ InternalRiskScore                   └─ balance
 └─ Accounts

Core vocabulary

ConceptQuestion it answers
Semantic modelWhat does this application expose?
IntentWhat does the caller want?
ResolutionWhat semantic entities, fields and relationships does the request refer to?
AuthorizationWhat may this actor exercise, and under which constraints?
PlanWhat provider-independent work must be performed?
ProviderHow is that work physically executed?
Result + evidenceWhat happened, and what execution facts can be inspected?

Why this matters for AI

An agent can be excellent at deciding what it wants without being an appropriate authority over database schema, tenants, credentials or business invariants.

AI agent
   ↓
structured capability intent
   ↓
Foundgine
 ├─ resolve
 ├─ validate
 ├─ authorize
 ├─ plan
 └─ execute
   ↓
provider

Capability discovery helps a model construct valid requests; it is not a grant of authority. The server evaluates authorization again for the actual operation.

An agent is also the clearest case for why a shared boundary matters in the first place: without one, each tool it can call is free to implement its own authorization and query logic, so an agent with dozens of tools can end up with dozens of independent security surfaces. Routing every tool through the same semantic and authorization path answers "what does this mean, and is this caller allowed to do it" once, consistently, no matter which tool the model called.

Multiple callers, one boundary

REST/API code, GraphQL, JSON, MCP and Microsoft.Extensions.AI integrations can all become intent sources while the semantic lifecycle remains the same. This prevents transport concerns from becoming duplicated execution semantics.

What it deliberately leaves outside

  • Authentication and identity lifecycle remain host/application responsibilities.
  • Distributed authority recovery is optional and isolated in Foundgine.Security.Authority.
  • Provider-specific physical behavior belongs in provider packages.
  • General autonomous agent orchestration is outside the core runtime.

What Foundgine is not

Foundgine is not an ORM replacement, database, GraphQL server, identity provider, authorization server, workflow engine or general autonomous-agent framework.

What, how, where — and what it's designed for

What: a semantic execution boundary between caller intent and physical execution.

How: every caller converges on one pipeline — Intent → Semantic Model → Resolution (including lexical grounding) → Authorization → Provider-independent Plan → Execution + Evidence.

Where: below the transport (GraphQL, JSON, MCP, AI, application code), above the provider (SQL, InMemory, or others). It replaces the layer where a controller or tool handler would otherwise hand-roll authorization and query construction — it does not replace the provider or the transport.

What it's designed for: applications where more than one kind of caller needs to reach the same data and operations, and where getting authorization or meaning wrong would be costly. The value scales with the number of callers, the consequence of a wrong decision, and how much of the input is free-form language rather than a fixed shape.

Categories of applications

  • Multi-transport enterprise backends — one hardened semantic/authorization core exposed through GraphQL, MCP, and JSON at once.
  • AI-agent tool execution boundaries — an agent proposes structured intent; Foundgine stays the authority over what it means and whether it's allowed.
  • High-assurance mutation workflows — writes where a wrong authorization decision is expensive enough to justify explicit dependency ordering, replay protection, and an execution receipt.
  • Composite / cross-domain application models — a semantic model assembled from more than one underlying physical concept.
  • Free-form / natural-language query surfaces — a search box, chat interface, or open-ended agent, where lexical grounding resolves language against the contract without letting retrieval relevance become authorization.

See What Foundgine is designed for for the full breakdown, with the sample project that proves each category.

Ambiguity is a first-class result, not a silent guess

Free-form language can be structurally valid against more than one meaning at once — “active customers” can legally mean an enabled account or a customer with a recent order, and a graph-constrained path can't tell those apart on its own. A resolver that always returns the top-scored candidate will occasionally execute a confidently wrong interpretation: a perfectly authorized misunderstanding.

Foundgine's SemanticLexicalResolver.Ground returns a GroundingDecision instead of just a winner: it commits when interpretations agree on meaning (even if they came from different retrieval evidence or graph routes), and requires clarification when they genuinely disagree. See Grounding decisions for the full explanation and a worked example.
