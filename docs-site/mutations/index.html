Foundgine / Mutations
Semantic mutation execution

Mutations are capabilities, not generated SQL.

A mutation can carry business invariants, authorization, dependencies, idempotency semantics, and provider-specific transactional execution without exposing those details to the caller.

A consequential example

The repository includes a high-assurance TransferFunds example because consequential mutations reveal whether an execution architecture is actually carrying business meaning.

TransferFunds
  ↓
resolve source + destination
  ↓
verify tenant + ownership
  ↓
verify account state
  ↓
verify limits + available funds
  ↓
verify idempotency
  ↓
transactional execution
  ├── debit
  ├── credit
  └── audit
  ↓
execution receipt

Business semantics remain explicit

The example does not equate available funds with raw balance. The semantic definition can account for pending transactions and regulatory holds:

available_funds
    = balance
    - pending_transactions
    - regulatory_hold

This illustrates the central point: Foundgine can execute a defined business invariant, but the application remains responsible for defining the invariant correctly.

PostgreSQL execution boundary

The PostgreSQL implementation uses a transaction for the mutation and locks the relevant account rows in deterministic order before re-reading current state. Idempotency is persisted in the database and audit information is written as part of the mutation boundary.

Atomicity

Debit + credit

The mutation is designed so the two sides of the transfer commit together or the transaction rolls back.

Replay safety

Idempotency

A repeated request with the same idempotency identity can return the existing execution rather than performing a second transfer.

Concurrency

Deterministic locking

Account locks use a deterministic order to reduce deadlock risk for opposing transfers.

Evidence

Audit + receipt

The execution boundary can produce evidence about what was executed rather than returning only a domain value.

Why this matters

CRUD examples can hide the hard part of application infrastructure. High-assurance mutations force the architecture to answer questions about authorization at execution time, concurrency, replay, domain invariants, transaction boundaries, and evidence.

What this does not prove

A single transfer example does not establish that every business mutation is safe. Other operations need their own semantic contracts, authorization rules, concurrency assumptions, and provider proofs.
