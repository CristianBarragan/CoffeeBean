Foundgine / Providers
Provider boundary

One semantic meaning. Different physical execution.

Foundgine's provider boundary exists so SQL, InMemory, and future providers do not redefine the application's semantic model.

SQL

The SQL path lowers provider-neutral execution into relational SQL and executes it through the configured SQL provider. PostgreSQL is the main database integration path in the repository and is covered by database-backed integration tests when configured.

InMemory

The InMemory provider intentionally does not generate SQL. It executes the logical model directly over CLR-backed data and is useful for proving that the semantic plan is not simply SQL disguised as an abstraction.

Adapters stay outside the core

Input adapter

GraphQL

GraphQL converts a transport-specific request into Foundgine semantics. The GraphQL layer is not the planner.

Input adapter

JSON

Structured JSON intent can be parsed, bounded, and resolved without giving JSON direct execution authority.

Caller

AI

AI integration supplies tools and structured intent. Trusted execution context remains owned by the host application.

Provider

SQL / PostgreSQL

The provider is responsible for physical execution while preserving the semantic and security contract passed to it.

Provider parity is earned

Provider independence does not mean every provider supports every operation. The repository explicitly treats provider support as a contract to be tested. A provider should only claim support for semantics it can execute correctly and preserve.

Adding a provider

1. Consume the provider-neutral execution contract
2. Declare supported operations
3. Preserve required security invariants
4. Compile logical operations into provider-native work
5. Validate result semantics
6. Add conformance + integration tests
