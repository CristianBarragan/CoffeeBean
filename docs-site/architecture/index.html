The first example is grounded in the repository's JSON read E2E. The AI-agent example is an architectural flow showing how an agent can use the same boundary without receiving database authority.

Why the boundaries matter

Caller → Intent

Different interfaces can describe the same operation without owning database semantics. JSON, GraphQL, REST or an AI tool can all become structured intent.

Intent → Semantic Model

The application decides what concepts exist and which relationships are meaningful. A semantic field does not have to be a physical column.

Semantic Model → Authorization

Authorization is applied to the semantic operation, before physical execution. This gives the application a single place to preserve field visibility, relationship visibility and security constraints.

Authorization → Execution Plan

The plan carries the authorized operation forward in a provider-neutral form. It is the boundary where planning, validation, rewriting and optimization can happen without giving the caller provider control.

Execution Plan → Provider

A provider translates the plan into physical execution. For SQL, that means parameterized SQL; another provider can implement the same semantic operation differently.

Provider → Result

The provider returns execution data through the same boundary. The caller receives the business result rather than gaining authority over the underlying storage engine.

Why the intermediate plan matters

The execution plan is the architectural boundary between semantic intent and physical execution. It gives the runtime a place to preserve authorization constraints, validate dependencies, rewrite operations, optimize safely, reason about provider capabilities and produce execution evidence.

That distinction is important: a caller can request a business operation without deciding whether the provider should use a join, a predicate pushdown, a batched mutation or another physical strategy.
