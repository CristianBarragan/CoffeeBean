System architecture

Architecture

The architecture is intentionally layered. Meaning is separated from planning; planning is separated from physical provider execution; transports are adapters rather than authorities.

Canonical lifecycle

The same lifecycle is used by every caller and provider. The full-size canonical architecture also shows retrieval as a parallel candidate-discovery stage.

Semantic layer

Foundgine.Semantics owns application meaning: entities, fields, relationships, typed and dynamic intent, resolution, validation, semantic capabilities and authorization. It remains provider-independent.

Metadata layer

Foundgine.Metadata describes structural facts that can be discovered or produced by AOT generation. It bridges CLR/storage structure into the semantic model without turning semantic code into reflection or ORM code.

Planning layer

Foundgine.Planning converts an authorized semantic operation into a provider-independent plan and then into ExecutionIR. Filters, ordering, pagination, traversal and aggregation remain logical. Physical joins, indexes and SQL constructs are provider decisions.

Execution layer

Foundgine.Execution is the final provider boundary. It verifies execution/security obligations, compiles or dispatches provider work, materializes results and can produce execution evidence.

Retrieval strategies inside Foundgine.Sql

Semantic candidate retrieval — ranked matches for an ambiguous reference — is one provider-neutral RetrievalStrategy contract with several PostgreSQL-backed strategies:

StrategyPostgreSQL mechanism
Fuzzypg_trgm
FullTexttsvector / websearch_to_tsquery
Searchoptional pg_search / BM25
GraphSimilarityoptional Apache AGE (Cypher over a semantic relationship)
Vectorreserved for a future pgvector provider

Search and GraphSimilarity only activate when their respective PostgreSQL extensions are installed. Every strategy produces candidates and evidence — the result still passes through ordinary semantic resolution and authorization before it can reach an execution plan.

Semantic Operation Graph → Authorization → Plan Binding → Execution

The semantic operation graph is the canonical security object for a resolved request. It gives authorization one complete object to evaluate before provider-specific planning begins.

Intent
  ↓
Semantic Operation Graph
  ↓
Validate + resource limits
  ↓
Authorize against semantic contract
  ↓
Authorized Graph + Evidence
  ↓
Semantic Plan
  │  └─ AuthorizationBinding
  ↓

  ↓

  ↓

  ↓
Final execution gate
  ↓

SemanticPlanAuthorizationBinding records the exact semantic contract fingerprint and authorization-decision fingerprint that produced the plan. Rewrites must preserve that binding. ExecutionIR and the provider plan inherit it, and the final security gate checks the exact provider artifact against the exact execution IR.

The invariant: an executable provider artifact must remain traceably bound to the semantic contract and authorization decision that produced it. A different contract, authorization decision, execution IR or provider security proof fails closed.

Retrieval mechanisms — relational lookup, pg_trgm, full-text, optional BM25 and optional Apache AGE graph similarity — can produce candidates and evidence for semantic resolution, but they never grant authority or bypass this lifecycle.

Lexical grounding and grounding decisions

Free-form language is resolved through a provider-neutral candidate boundary (Foundgine.Elasticsearch, Foundgine.Postgres.Vector): every token is scored across semantic kinds, and the highest score is a hypothesis, not truth — the semantic graph decides whether a path is legal.

A legal path is not automatically the intended one, though: the same expression can be structurally valid against two different meanings at once (a different field, value, relationship, or root entity), and retrieval score alone can't break that tie safely. SemanticLexicalResolver.Ground returns a GroundingDecision that tells competing meanings apart from duplicate evidence for the same meaning, and requires clarification instead of silently authorizing the top-scored candidate when two or more meanings remain genuinely tied. See Grounding decisions.

Why the intermediate plan matters

The plan is where authorization can be preserved while optimization and provider capability reasoning occur. A provider can optimize physical execution without changing the application's semantic contract.
