Advanced semantic reference

Foundgine Supply Chain — Complex Semantic Showcase

The intentionally difficult reference vertical for Foundgine. It exercises the semantic execution boundary rather than demonstrating ordinary CRUD.

Why the semantic boundary matters

A persistence model describes how data is stored. A semantic model describes what the application exposes, what relationships and business concepts are available, and what operations the system is willing to execute.

The caller should express business intent. It should not choose database tables, inject tenant predicates, bypass authorization, construct provider-specific SQL, remove semantic constraints, or disable traversal limits.

This sample makes that distinction concrete by combining recursive data, authorization constraints, temporal state, aggregation, mutation dependencies, and deliberately hostile domain cases.

Manual and generated semantic models

The sample distinguishes two ways of creating the semantic surface: manual semantic authoring and generated semantic metadata. Both produce the same provider-independent semantic representation and use the same resolution, authorization, planning, and execution pipeline.

Manual: author semantics against the domain model

new SemanticModelBuilder()
    .Entity<Product>(Product, "Product", e => e
        .Identity(x => x.Id)
        .Field(x => x.Sku)
        .Field(x => x.Name)
        .Field(x => x.SafetyStock));

The x in these selectors is the application/domain model type, such as Product. It is not the semantic entity builder, an EF entity metadata object, or provider metadata. Foundgine derives the property name and CLR type and allocates the entity-local FieldId, so manual semantic definitions do not need new FieldId(2) or repeated typeof(string).

Type both sides of a relationship

.Relationship<Product, ProductComponent>(
    Product, new RelationshipId(1), "components",
    product => product.Id,
    Component, component => component.ParentProductId,
    RelationshipCardinality.Many)

Manual relationships use an explicit <fromEntity, toModel> generic pair. The first selector is compiled against the source domain model and the second against the target domain model. That distinction is intentional: product => product.Id is a property on the application model, not entity.Property(...) on an EF/storage entity. Foundgine validates that both selectors are direct model properties and that their CLR types match. This makes both sides strongly typed and prevents source/target property mix-ups before execution.

Model property, not entity metadata. Manual semantic lambdas should read like model => model.Property. They should not depend on EF EntityType, Property, column metadata, or numeric FieldId values. Storage mapping remains a separate concern.

Why the generic pair matters

<fromEntity, toModel>
       │       │
       ▼       ▼
 product =>   component =>
 product.Id    component.ParentProductId
       │       │
       └── typed relationship ──┘

The compiler now knows the type of each lambda independently. A property belonging to the target model cannot accidentally be selected from the source model, and a storage-layer property cannot be substituted for a domain-model property. The generated approach derives the same relationship information automatically; the manual approach makes the intent explicit.

Generated: derive semantic handles from model metadata

Domain / declared model
        ↓
Foundgine generator
        ↓
Generated semantic handles
        ↓
Same SemanticModel / execution pipeline

Generated semantics remove repetitive hand-written mapping when the application's semantic surface can be derived safely. Manual semantics remain useful when the exposed surface needs deliberate curation or when semantic names and capabilities intentionally differ from the underlying model.

The important distinction is authoring strategy, not runtime architecture: both approaches converge on Foundgine's semantic model before resolution, authorization, planning, and provider execution.

Authorization is part of the semantic example

This sample intentionally demonstrates authorization as a semantic concern rather than as a transport-only role check. The policy surface has several independent boundaries, and a request must survive all of the applicable boundaries before it can become an executable plan.

Annotations describe; policies decide

The domain models use small declarative annotations such as [SemanticEntity], [SemanticField], and [SemanticPolicy("...")]. These are source metadata for the semantic/generation path. They are deliberately not the final authorization decision. 

Annotations / generated metadata ─┐
Manual semantic definitions ──────┼──> SemanticModel
                                  │
Current actor policy ─────────────┘
                                      ↓
                               Authorization
                                      ↓
                            Semantic Plan / IR
                                      ↓
                                  Execute

The runtime policy is SupplyChainAuthorizationPolicy. Capability discovery is descriptive only: an agent may inspect what is available, but a capability response is never treated as proof of authority. The current policy is evaluated again for the requested operation.

Mixed manual + generated authoring

The SupplyChain model deliberately mixes authoring strategies. Purchase orders, purchase-order lines, and shipments are represented by the generated artifact; products, suppliers, inventory and the other curated domain concepts are manually authored. The two paths are imported into one SemanticModel before resolution and authorization.

                          ├──> one SemanticModel

MCP adversarial client — Run 5 style

The sample includes a small protocol-level MCP client that treats the MCP boundary as hostile. It sends ordinary tools/call requests, but deliberately attempts to cross each policy boundary. This is intentionally similar to the high-assurance adversarial shape used in Run 5 of the agent benchmarks: the caller is untrusted, the tool surface is real, and authorization must hold at execution time rather than relying on what the caller previously discovered. 

describe_capabilities
        ↓
Cross-tenant probe ────────> DENY
Sensitive field probe ─────> DENY
Relationship escalation ───> DENY
Write escalation ──────────> DENY
Named operation escalation ─> DENY
Unauthorized write ────────> DENY
Authorized operator write ─> ALLOW

The important security property is not merely that the MCP endpoint has a role check. The semantic policy survives capability discovery, intent resolution, relationship traversal, planning, and execution. A caller cannot provide its own tenant predicate, turn a denied field into an allowed field, or convert read authority into mutation authority.

Client-supplied claims — narrowing, never widening

read_entity, write_entity, and policy_probe also accept an optional, untrusted claims dictionary sent by the MCP caller itself, on top of the existing actor/token authentication. Identity — tenant and role — is still resolved entirely server-side; claims are additional context a caller volunteers about itself, and a new fail-closed ClientClaimsValidator is the only thing standing between that untrusted dictionary and the authorization policy. 

Client claims (untrusted) ──> ClientClaimsValidator ──> Accepted claims only ──> SupplyChainAuthorizationPolicy
                                     │
                                     └──> Rejected claims (reported, never consulted)

The validator treats every claim as hostile until proven otherwise. Reserved identity keys are never accepted under any circumstances — not even when the asserted value happens to match the caller's real identity — because their presence alone is the attack: a well-formed caller has no reason to assert its own identity through a side channel. Recognized non-identity keys are validated against a strict per-key format and rejected individually on a bad value; unrecognized keys are dropped individually and reported back rather than failing the call. Evidence claims are cross-checked against their own expiry, so stale evidence cannot substitute for current authorization.

ClaimEffectDirection
scope=read-onlySelf-imposed write restriction for that call.Narrowing
warehouse=<id>ANDs a warehouse-id predicate onto the existing tenant predicate for Warehouse/InventoryLot reads.Narrowing
reason, change_ticketRequired evidence for the manager-only inventory.reconcile named operation, on top of the existing role check.Additional gate
role, tenant, actor, isAdmin, permissions, …Presence alone fails the entire call closed.Spoofing attempt

Every accepted claim can only narrow what the authenticated role already allows — the warehouse predicate is combined with AND, never OR, so it can only shrink a result set, and the two-argument SupplyChainAuthorizationPolicy constructor used everywhere else in the sample is unchanged and simply delegates to an empty claim set. There is no code path from a rejected or malformed claim into an authorization decision. The adversarial MCP client exercises this directly: role/tenant injection and missing, malformed, or expired reconcile evidence are attacks that must be denied, while a self-imposed read-only scope, a warehouse scope, an unrecognized claim key, and well-formed reconcile evidence are legitimate, self-narrowing uses that the policy must honor rather than silently ignore.

See the sample's GUIDE.md for the full validation rules, the policy wiring, and the complete attack/legitimate-use matrix.

Optimization is required to preserve the resolved operation and its security constraints. Projection reduction, predicate composition, relationship pruning, bounded traversal, ordering, and aggregation may change the physical plan, but must not remove authorization predicates, semantic constraints, or resource bounds.

Scenario 1 — Deep supply-chain investigation

This scenario crosses several relationships: product → component → supplier → purchase order → shipment → inventory. It demonstrates multi-hop traversal, relationship resolution, projection shaping, predicate composition, and execution-plan construction.

The caller expresses a business question rather than constructing joins or SQL. Foundgine resolves the request against the semantic model and builds a provider-independent representation before execution.

Scenario 2 — Recursive supplier risk

BOM relationships are recursive and the seed data deliberately contains a cycle: 

Product A → Component B → Component C → Product A

The traversal therefore demonstrates bounded depth, visited-node tracking, deduplication, deterministic traversal, and deliberate cycle detection. Depth limits and visited-node tracking also help prevent recursive intent from becoming an unbounded resource-consumption path.

Scenario 3 — Fulfillment planning

The planner must distinguish physical inventory from inventory that is actually usable. It considers available quantity, reservations, quarantine, inbound shipments, shipment state, temporal constraints, aggregation, ordering, and authorization. 

Customer Order
      ↓
Required Product
      ├── Available Inventory
      ├── Reserved Inventory
      ├── Quarantined Inventory
      └── Inbound Shipments

This demonstrates that business availability is a semantic concept, not merely a database row-existence check.

Scenario 4 — Transactional mutation planning

The domain is structured for generated mutation dependency graphs such as: 

Purchase Order
      ↓
Purchase Order Lines
      ↓
Shipment
      ↓
Inventory Lot
      ↓
Inventory Movement

The semantic model describes what the mutation means. The planner determines a valid dependency order, while the execution layer can apply that order using the provider's transactional capabilities.

Scenario 5 — Adversarial security and state

The sample deliberately includes cross-tenant warehouse data, expired certifications, and BOM cycles alongside delayed and partial shipments, cancelled purchase orders, and quarantined inventory.

A warehouse can exist in the semantic model without being accessible to the current actor. Likewise, an existing certification is not necessarily valid if its validity period has expired. Semantic execution therefore has to consider both what exists and what is valid and accessible.

Deliberately hostile data

  • BOM cycle: exercises bounded traversal and cycle detection.
  • Delayed shipment: tests temporal filtering.
  • Partial shipment: tests quantity aggregation and remaining demand.
  • Cancelled purchase order: tests semantic state filtering.
  • Quarantined inventory: tests business availability versus physical existence.
  • Cross-tenant data: tests authorization boundaries.
  • Expired certification: tests temporal semantic constraints.

Layer-by-layer architecture

Domain model

Defines business concepts such as Product, Supplier, Warehouse, Shipment, and InventoryLot.

Semantic metadata

Describes application-facing fields, relationships, operations, predicates, and capabilities in a machine-reasonable form.

Intent

Represents what the caller wants without binding the request to a database provider or physical schema.

Resolution

Maps requested intent onto the semantic model and rejects invalid operations before execution.

Authorization

Applies security constraints to the resolved semantic operation. Authorization constraints remain part of the operation that subsequent optimization must preserve.

Safe optimization

Allows projection reduction, predicate composition, relationship pruning, bounded traversal, ordering, and aggregation while preserving the meaning, security constraints, and resource bounds of the resolved operation.

Execution IR

Provides the provider-independent boundary between semantic planning and physical execution.

Provider lowering

Only at the final stage does provider-specific execution enter the system, such as PostgreSQL SQL generation.

In-memory execution

The current sample contains a deterministic in-memory scenario evaluator so domain and semantic behavior can be exercised without external infrastructure. This makes the semantic layer independently testable rather than requiring every scenario to start with a database.

The semantic model is intentionally shaped like the generated artifact, leaving room for a future AOT semantic generator to replace hand-emitted semantic artifacts.

Run the sample

dotnet run --project samples/Foundgine.SupplyChain.Semantic

No external database is required for the basic deterministic scenario evaluation.

How this sample fits the Foundgine architecture

Use Getting Started and the Supply Chain sample to understand the physical application layers first.

Then use this sample to understand why a semantic boundary exists: it separates caller intent from persistence details while providing a place to resolve relationships, apply authorization, enforce traversal limits, reason about temporal state, optimize safely, and construct executable plans.

Finally, use the PenTest sample to examine what happens when the same application is exposed through multiple transports and those transport boundaries are subjected to security regression testing.

Next step
