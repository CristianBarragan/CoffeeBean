Get started with Foundgine

Run the Foundgine.SupplyChain sample end to end, then walk through the architecture from the MCP boundary and application authorization layer to semantic planning and PostgreSQL execution.

What you'll build and run

The canonical Supply Chain sample exposes a supply-chain domain through MCP while keeping transport, application, authorization, semantics, planning, and persistence concerns separate. 

Agent / MCP client
        ↓
      API
        ↓
   Application
        ↓
Domain + Semantics
        ↓
Planning / Execution
        ↓
   Foundgine.Sql
        ↓
   PostgreSQL

The purpose of the sample is not simply to demonstrate database CRUD. It shows how a structured caller intent can cross a controlled application boundary and become a provider-specific database operation without making the transport responsible for business security.

1. Prerequisites

  • .NET 9 SDK
  • Docker
  • A clone of the Foundgine repository

2. Start PostgreSQL

cd samples/Foundgine.SupplyChain
docker compose up --build

3. Run the API

If PostgreSQL is already running:

dotnet run --project samples/Foundgine.SupplyChain/Api/Foundgine.SupplyChain.Api.csproj --urls http://localhost:4422

Check the application health and readiness endpoints:

curl http://localhost:4422/health
curl http://localhost:4422/health/ready

The MCP endpoint is http://localhost:4422/mcp. MCP tools are thin transport adapters over SupplyChainApplication; they do not contain SQL or duplicate business authorization.

4. Walk the architecture

API and MCP boundary

The API layer creates the ASP.NET host, registers dependencies, exposes MCP and health endpoints, and forwards structured requests into the application layer. It contains no SQL and does not own business authorization.

Application and authorization

SupplyChainApplication defines the use-case boundary. It authenticates the actor and token and applies capability authorization before delegating to query or mutation ports.

This central boundary is important when multiple transports exist: adding another transport should not require copying security rules into another adapter.

Domain model

The domain contains storage-oriented ERP records and application-facing domain models. Semantic names remain independent from physical table and column names, allowing application intent to remain stable when persistence details change.

AOT metadata

Foundgine.Aot.Generator turns annotated domain declarations into generated metadata at compile time. The generated representation supplies machine-readable information to the semantic layer without requiring runtime reflection for the normal path.

Semantic model

SupplyChainSemanticModel provides stable semantic entities, relationships, fields, predicates, and operations. Application code can build semantic operations without depending directly on database table and column names.

The semantic model is the application-facing contract: it describes what the system exposes and what operations can be executed, rather than merely describing how rows are stored.

Planning and infrastructure

Query and mutation repositories build semantic operations that flow through Foundgine planning and provider execution rather than embedding SQL for the normal path. Planning can resolve relationships, compose predicates, shape projections, and preserve application constraints before provider-specific execution.

High-assurance mutations

Operations such as place_order and cancel_order retain explicit parameterized PostgreSQL SQL where provider-specific transactional invariants require it. Semantic execution therefore does not mean hiding every database operation behind an abstraction when explicit SQL provides the stronger guarantee.

Testing

Tests validate authorization, generated metadata, semantic plans, SQL compilation, PostgreSQL integration, and transport contracts. The dedicated PenTest sample extends this story with transport-level security regression tests against MCP and GraphQL.
