Fixed endpoint vs dynamic capability: batching changes the unit of work.

Run 5 compares a fixed, operation-specific EF Core endpoint with Foundgine's dynamic semantic batch endpoint. Both run over MCP against PostgreSQL and enforce the same high-assurance transfer semantics, but they do not expose the same execution capability.

The headline result

EF Core980.1 ops/ssingle-transfer endpoint
Foundgine10,731 ops/s64-operation UNNEST batch
Throughput10.95×+994.8% vs EF Core
Amortized latency~2.82 msFoundgine batch wall ÷ 64

Interpretation: this shows the value of making the capability dynamic and set-oriented. It does not mean a single Foundgine transfer is 11× faster than a single EF Core transfer.

Why this test is important

This benchmark intentionally compares two different endpoint models. The EF Core side is a fixed endpoint: its MCP tool is written specifically for one TransferFundsCommand and processes one transfer per call. The Foundgine side is a dynamic endpoint: the capability accepts an array of commands and Foundgine lowers that request into a set-based PostgreSQL execution.

That capability difference is intentional. The question is whether a semantic execution engine can turn many logical operations into one database-oriented execution without requiring every application endpoint to be hand-written as a batch API.

Fixed EF Core endpoint

  • One transfer command per MCP call.
  • Pre-written operation-specific workflow.
  • EF Core change tracking and SaveChangesAsync().
  • No batch tool for this capability.

Dynamic Foundgine endpoint

  • Array of transfer commands per MCP call.
  • Capability is lowered dynamically.
  • Typed PostgreSQL UNNEST arrays.
  • One set-oriented database mutation for the batch.
Important fairness note: EF Core does not provide a portable first-class FOR UPDATE row-lock API through its normal LINQ abstraction. To make this a high-assurance comparison, the EF implementation was explicitly modified to use PostgreSQL raw SQL SELECT ... FOR UPDATE reads plus the same transaction-scoped advisory idempotency lock used by the PostgreSQL implementation. This means the baseline is not plain out-of-the-box EF Core; it is EF Core augmented with explicit PostgreSQL locking.

Why the locking adaptation matters

The EF baseline uses a transaction, an advisory lock for the idempotency key, deterministic account ordering, and raw SQL FOR UPDATE reads. EF then tracks those rows, applies the state transition, inserts idempotency/audit records, and calls SaveChangesAsync().

That explicit locking was added because the benchmark is testing the same high-assurance concurrency contract on both sides. Without it, the EF implementation would have a different locking model and the comparison would mix execution-engine differences with a weaker concurrency guarantee.

Read the latency correctly

One EF Core MCP request represents one logical transfer. One Foundgine MCP request represents 64 logical transfers. Therefore the raw 180.5 ms Foundgine batch latency is not an apples-to-apples comparison with EF's 45.3 ms single-transfer latency.

The useful throughput measure is logical operations per second. For a per-operation view, the batch wall time is amortized across its 64 operations: 180.5 / 64 ≈ 2.82 ms. The benchmark reports both numbers deliberately so the batching benefit is visible without hiding the actual batch tail latency.

What this proves — and what it does not

  • It does show: dynamic batching can dramatically increase logical mutation throughput when many commands can be lowered into one PostgreSQL set operation.
  • It does show: the application does not need a separate hand-written fixed batch endpoint to expose this execution shape.
  • It does not show: that a single Foundgine transfer has 11× lower wall latency than a single EF Core transfer.
  • It does not show: that Foundgine's batch p99 is lower than EF Core's single-operation p99. The units differ.
  • It does not represent: vanilla EF Core with no explicit PostgreSQL row locks.

Next experiment

The next useful matrix is batch size: 1 → 8 → 16 → 32 → 64 → 128 → 256 → 512 → 1024. That will show where batching stops scaling, where tail latency begins to dominate, and whether the dynamic execution model continues to outperform a fixed endpoint as the logical mutation graph grows.
