End-to-end evidence · Run 2

Same process, corrected verifier, one honest crash.

Run 2 repeats the customer-exposure-review scenario from Run 1, but the verifier now checks Conventional and Foundgine separately instead of pooling their pass/fail counts, and every concurrency tier — including the one that crashed — was traced back to a root cause instead of being reported as a single "failed" number.

Run 1 · Concurrency baseline Run 2 · Correctness, crash forensics & cost

Process

10 customers, replay mode, 5 warmups and 30 measured runs per tier, at concurrency 8 → 16 → 32 → 64. Same fixture as Run 1: 4 relationships, 12 contracts, 48 transactions, $48,240.00 exposure per customer. The scenario resets every customer to a known baseline before every single run, executes query → mutation → query → mutation, and compares the resulting database row against an explicit per-customer expected state.

What changed from Run 1: the verifier used to report one pooled Verification failures: N count across both flows, which made it impossible to tell whether Foundgine or the conventional baseline caused a given failure. Run 2's report tags every verification record with its flow, so pass/fail can be split out per implementation.

Results — correctness, split by flow

Conventional and Foundgine choreography use the same GraphQL API and provider underneath; the only difference is how many round trips the agent needs to reach the same final state. Foundgine reduced that from 9 tool calls/flow to 6 (33.3%) and estimated context-load tokens from ~1,165 to ~856 per flow (~26.5%) — consistent across every tier.

Why the conventional baseline failed, not Foundgine

The fixture only has 10 customers. At concurrency 16 and above, customer IDs are deliberately reused across concurrent flows — the console log flags this: concurrency exceeds available customers; customer IDs will be reused. That means several flows run query → mutation("Reviewed") → query → mutation("Remediation Complete") against the same customer row at the same time. Some of those racing flows finish with the last mutation applying "Reviewed" again instead of "Remediation Complete" — a genuine race in the test's write pattern, not data corruption. The failure count tracks that exactly: 0 at C=8 (no reuse), 1 at C=16, 27 at C=32. Whatever mechanism the Foundgine path used to sequence its two mutations per flow did not lose the second write under the same contention.

Results — the concurrency-64 crash

Concurrency 64 did not fail on correctness. It crashed the benchmark process outright, on Foundgine run 12 of 30, with:

System.Net.Sockets.SocketException (10048): Only one usage of each socket
address (protocol/network address/port) is normally permitted. (localhost:4302)

Root cause: the harness opens a brand-new HttpClient for every single GraphQL call — every query and every mutation, in both flows — instead of reusing one. Under concurrency 64 that's up to a few hundred near-simultaneous socket opens/closes against localhost:4302; Windows holds closed sockets in TIME_WAIT long enough that the ephemeral port pool ran out. This is a benchmark-harness bug shared by both flows, not a Foundgine-specific fault — but it very likely also explains why Foundgine's average wall time was climbing tier over tier even before the crash (517 ms → 984 ms → ~627 ms across the last completed runs): each of its "fewer" tool calls was still paying a full TCP handshake.

Because the report is only written once, after all flows and runs finish, the crash also means the 11 completed Foundgine runs and all 30 completed Conventional runs at concurrency 64 were never serialized to a comparable JSON report — they exist only as console text, unverified. That data is lost, not corrected; a rerun is needed once the harness reuses a single HttpClient.

Outcome

Correctness finding: PASS for Foundgine. 100% of completed Foundgine flows reached the expected final state at every tier; the conventional baseline degraded under its own concurrent-write race.
Efficiency finding: PASS. 33.3% fewer tool calls, ~26.5% lower estimated context load, holding steady from C=8 through C=32.
Latency finding: NOT A WIN. Foundgine's wall time stays 3–4× higher than the conventional baseline in this replay harness.
Infrastructure finding: HARNESS BUG. The concurrency-64 crash is a socket-exhaustion defect in the benchmark client (per-call HttpClient construction), not a correctness or capacity limit of Foundgine.

Token usage, cost & power (illustrative)

This run executed in replay mode: no live model calls were made, so provider-reported token, dollar and energy usage are all zero by construction. The only real number available is estimated context-load tokens — a heuristic (max(chars/4, words×1.3)) applied to every recorded tool input/output payload. What follows extrapolates that heuristic to illustrative dollar and energy figures if this context load were sent to a live LLM. These are scenario numbers with stated assumptions, not measured billing or utility data — swap in your own provider's per-token rate and your own energy figure to get numbers that apply to your deployment.

Assumptions used below: $3.00 per 1M tokens (a round, illustrative blended rate) and 0.30 Wh per 1,000 tokens (a commonly cited rough midpoint for LLM inference energy; published estimates vary roughly an order of magnitude depending on model size, so treat this as directional only).

Because both cost and energy are derived linearly from the same context-load token count, the saving is the same ~26.5% at every scale — it directly tracks the tool-call reduction, not a separate measurement. Note the trade-off this page already surfaced: fewer tokens and fewer tool calls did not translate into lower wall-clock time in this harness. Cost/energy and latency are separate axes here, and only one currently favors Foundgine.

What would make this stronger

  • Rerun concurrency 64 after fixing the per-call HttpClient allocation, to get a real (non-crashed) data point at that tier.
  • Rerun at customer counts that match or exceed concurrency (100/1,000/10,000 customers) so higher concurrency tiers stop reusing customer IDs, isolating pure throughput/latency from the write-race effect described above.
  • A live-mode run with provider-reported tokens would replace the illustrative cost/energy table with real API usage and billing numbers.
