AI agents · End-to-end evidence

Same business task. Same final state. Different boundary.

This benchmark asks a practical question: how much work must an AI agent do itself to complete a complex business operation, versus how much can be delegated to an application-controlled semantic execution layer?

The comparison is not simply about speed. The benchmark separates agent effort (context, model calls, tool calls and payloads) from application execution (CPU, memory and elapsed time). Both flows must produce the same final business state before the comparison is considered valid.

The scenario

A realistic customer review is deliberately more complicated than a single query. Customer 1 has 4 banking relationships, 12 contracts and 48 transactions. The task requires exposure analysis, concentration analysis, top-contract analysis, a threshold decision, a mutation and final verification.

Customer
  ├── 4 banking relationships
  │     └── 12 contracts
  │            └── 48 transactions
  │
  ├── calculate total exposure
  ├── analyse concentration
  ├── identify top contracts
  ├── compare with $48,000 threshold
  ├── mark customer as reviewed
  └── verify final state

Tokens vs. API time vs. application load: the full picture

These are three different measurements. A flow can win on one and lose on another, and none of them substitutes for the others:

TokensHow much context the agent carriesThe size of what the agent reads and writes — drives per-call API cost and context-window pressure.
API / model timeHow long the model spends thinkingWall-clock time actually billed to inference. Moves with tokens, but not proportionally.
Application loadHow long the system takes to executeTool calls, database work, the semantic engine — can go up even when tokens go down.
CorrectnessSame result, or it doesn't countNone of the above matters if the two flows don't reach the same final state.

This published result was captured in replay mode, which never calls a model — so the harness's own provider-reported token counts are correctly zero, not evidence of "no difference." The table below is fetched live from the same JSON report and adds an offline, heuristic token-load estimate computed from the recorded tool payload sizes, so the token dimension isn't a blank instead of a signal.

What if this ran at data-center scale?

Every number on this page so far is one paired scenario, replayed 10 times, on one fixture. The question worth asking next is directional, not precise: if a meaningful slice of the world's agentic AI traffic looked like the conventional flow above — an agent rediscovering schema and hauling raw rows through its own context instead of using an authorized semantic boundary — what would a ~61-63% cut in that traffic's token load be worth in electricity, not just dollars? This section is a napkin calculation, built from public 2026 data-center energy figures, explicitly so it can be checked and argued with rather than quoted as fact.

1.1 TWh/year is roughly the annual electricity use of a small country's single mid-size city, or about 100,000 average US homes — offered as a sense-of-scale comparison, not a precise conversion. At a global average grid intensity of roughly 0.4-0.48 kg CO₂/kWh, that same 1.1 TWh corresponds to very roughly 450,000-530,000 tonnes of CO₂e avoided per year, scaling linearly with the other two rows. None of these percentages (1%, 5%, 10%) is a measured or claimed figure — they are scenario inputs you should argue with, not conclusions. The only measured fact underneath all three columns is the ~62.9% token-load reduction from section 6 of the technical report, on this one scenario.

The honest takeaway isn't a headline number — it's the shape of the argument: agentic AI's energy footprint is dominated by how much an agent has to read and re-read to get its bearings, not by the business logic itself. A semantic execution boundary that resolves the graph once, behind the application, rather than making the model walk it turn-by-turn, is a lever on that footprint whether the unit you care about is a dollar, a token, or a kilowatt-hour.

Guardrails: efficiency is not the same as autonomy

A faster, cheaper agent is not automatically a safer one, and this benchmark is deliberately silent on that question — so it's worth being explicit about it here. Collapsing seven tool calls into four, and cutting the tokens an agent has to carry, does not by itself change what the agent is authorized to do. That has to be designed in, separately, on purpose:

Application stays the authorityNot the modelFoundgine's semantic capability and mutation boundary are application-defined. The agent requests intent; it never gets raw SQL or physical schema access, so a cheaper path can't become a wider one.
Mutations require explicit intentNo implicit writesThe benchmark's own scenario only mutates Customer.FullName because that's the one field the capability allows — narrower tool surface, narrower blast radius, independent of token count.
Verify after every mutationTrust, but checkBoth flows call a verification step after the update in this benchmark. Fewer tokens should never mean fewer checks — cheap and unverified is a worse trade than expensive and confirmed.
Same-final-state is the gateCorrectness firstEvery efficiency number on this page is reported conditional on SameFinalState: true. An efficient agent that reaches the wrong state is not a result — it's a regression that happens to look fast.

Put plainly: token and dollar savings are a side effect of giving an agent a narrower, application-controlled interface to work through — not a goal to chase by loosening what the agent can do on its own. The efficiency case for a semantic execution boundary and the safety case for one are the same case, not a trade-off between them.

Why this matters for AI agents

In the conventional flow, the agent has to discover the physical application surface, request pieces of the graph, keep those results in context and decide how to combine them. As the graph becomes larger, this creates more opportunities for lost context, repeated work, incorrect assumptions and hallucinated fields.

In the Foundgine flow, the agent works against a semantic capability. Foundgine resolves the business graph, applies the application's execution boundary, builds the plan and invokes the provider. The agent can therefore spend more of its reasoning budget on the business decision instead of reconstructing the application's data model.

Current benchmark status

Benchmark completed successfully. Both flows completed the same scenario and produced the same final state. Foundgine used 4 tool calls versus 7, a 42.9% reduction, and an estimated ~63% lower token load per the heuristic above. In this replay, Foundgine's wall-clock time was higher — fewer, smaller round trips for the agent traded against more work done inside the application boundary. The technical report shows the complete measurements and the reasoning behind that trade-off.

If this became the default pattern: a 50-year projection

Read this section as an argument, not an answer. Everything above this point on the page is either a direct measurement (tool calls, final state) or a heuristic applied to recorded data (token load, $ cost). Everything in this section is neither — it's a compounding scenario built on public growth forecasts and named assumptions, run 50 years forward. Fifty years is long enough that hardware efficiency, grid decarbonization, new architectures, and AI usage patterns could each individually swamp this entire estimate. It exists to show shape and scale, not to be quoted as a number.

The question we're illustrating: if a growing share of the world's agentic AI traffic adopted a semantic-execution-boundary pattern like the one measured in this benchmark, and data centers grow roughly along their published trajectories, what's the order of magnitude of electricity, dollars, and CO₂ over 50 years?
