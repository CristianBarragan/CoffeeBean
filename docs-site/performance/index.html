Evidence · scoped claims

Performance and benchmark evidence

Foundgine's performance claims are workload-specific. The benchmark pages publish exact experiment definitions and distinguish measured values from estimates.

What the evidence is for

The most useful question is not “is Foundgine universally faster?” It is whether the semantic execution boundary can reduce agent-side coordination while still providing a viable physical execution path.

Agent-work evidence

Published runs show repeated reductions in tool calls and estimated context load for the tested customer-exposure workflows. Those are architectural measurements, not universal claims about every agent or model.

High-assurance mutation evidence

The TransferFunds experiments test a richer capability with tenant isolation, ownership, authorization revalidation, account-state checks, idempotency and atomic transactional behavior. Run 5 exposed a concurrency limitation; Run 5b then isolated request shape with the same client and showed the benefit of a single semantic batch call. The honest conclusion is that semantic batching can be highly effective, while individual mutation endpoints still require workload-specific engineering.

Database/query evidence

The repository also contains controlled PostgreSQL graph-query measurements. They should be interpreted as evidence for the tested schema, fixture, provider and host configuration—not as a universal benchmark against every ORM or database design.

How to read the benchmark

  1. Read the experiment question.
  2. Check the exact workload and concurrency.
  3. Separate measured timing/RPS/tool-call values from estimated context metrics.
  4. Inspect success/failure counts.
  5. Do not generalize beyond the published workload.

Open the Agent Benchmark explorer for the experiment matrix and individual findings.
